# 统一项目助手

项目助手使用一个输入框和会话历史，支持自然聊天、项目问答、任务规划和需求检查。自动模式下，模型可直接回答或调用读取、规划、检查工具；Agent 循环使用 LangChain `create_agent`，不另设意图分类模型。输入区也可明确选择「任务规划」或「需求检查」，服务端直接执行对应流程，不再请求聊天模型判断用途。

项目导航收为「项目概览 / 任务看板 / 知识库 / 项目助手」。旧 `tab=planning`、`tab=assistant` 链接仍打开项目助手并预选相应用途，`tab=chat` 继续打开助手。正文内的结果卡片可打开右侧详情；手机上详情在下方展开。草案编辑、提交这一版和审批状态复用现有能力；草案与审批历史在助手抽屉内查看。

## 会话上下文

每段聊天只使用自己的历史和摘要。点击「新对话」创建空上下文；「历史」可以继续或删除旧会话。刷新、重新登录、服务重启后仍可继续原会话。URL 的 `chat_session` 指定当前会话，未指定时加载当前项目最近更新的会话。会话列表每页50条，消息每页40轮，支持向前翻页。

不提取用户偏好或跨会话项目记忆，没有记忆设置、记忆面板、自动提取队列或“记住”写入指令。在一段会话中说过的信息可以用于这段会话的追问，新会话不会继承它。

- `chat_sessions` 保存业务会话信息、执行状态和最后成功的 `checkpoint_id`。
- `chat_messages` 保存原始问答、本轮 `intent`、来源/任务快照、草案关联和检查报告快照，以及重试编号；一行代表一轮问答。
- LangGraph 官方 `AsyncPostgresSaver` 保存 Agent 上下文，线程标识为服务端生成的 `chat:{session_id}`，与审批线程隔离。身份和项目归属在读写检查点前校验，客户端不能提交检查点或历史。
- LangChain `SummarizationMiddleware` 在上下文达到30条消息或约8000 tokens时摘要较早的历史，配置保留最近20条消息；工具调用与工具结果也计入消息，框架会处理配对边界。摘要提示要求最多3000字符，框架不会将这个提示当作严格长度验证。原始问答表不受摘要影响。

下一轮显式从数据库记录的成功检查点继续。失败、取消、引用校验失败或答案保存失败时，框架可能已产生中间检查点，但这些检查点不会被下一轮采用。首次问答失败后的重试同样从空上下文开始。检查点缺失时可用原始成功问答和工件概要重建上下文，再由框架处理摘要。历史工件仅帮助理解追问，后续规划、检查和项目查询仍重新读取当前资料。

删除会话调用官方检查点删除 API，并删除原始消息和会话记录。回答尚未结束时删除返回409，避免并行写入重新产生上下文；停止或等待结束后可删除。

## 接口与执行状态

以下路径均以 `/api/v1/projects/{project_id}/chat` 为前缀，要求成员登录并验证项目归属。

| 接口 | 用途 |
| --- | --- |
| `GET`（前缀本身） | 模型配置、资料数量 |
| `GET /sessions?offset=0` / `POST /sessions` | 会话列表 / 新建会话 |
| `GET /sessions/{id}?before={seq}` / `DELETE /sessions/{id}` | 历史分页 / 删除会话与上下文 |
| `POST /sessions/{id}/messages` | 保存问答并返回完整 JSON |
| `POST /sessions/{id}/messages/stream` | 保存问答并返回 NDJSON v1、`kind=chat` |

发送参数为：

```json
{
  "question": "那我们项目有没有相关规则？",
  "client_message_id": "6b2426fb-5f73-46d3-b1a2-ae1fbb3a6412",
  "intent": "auto"
}
```

`intent` 可省略，默认 `auto`；另外两个值为 `task_planning`、`requirement_check`。问题限1～2000字符。前端为新问题生成 UUID，重试复用同一编号和用途。成功消息重试直接返回保存结果；同一编号更换问题或用途返回409。每个会话同时处理一条消息，短事务中的会话行锁与245秒租约用于协调，模型等待期间不占用业务查询的数据库连接。失败或取消后可原位重试最后一条问题；开始其他问题后，旧的失败问题需要作为新消息发送。

助手调用预算210秒，完整会话处理220秒，流式边界230秒，浏览器等待240秒；规划子流程仍限120秒，检查子流程仍限65秒，各自模型调用上限保持有效。普通闲聊不因为这些预算增加额外模型请求。提交消息、工件关联和成功检查点编号后才发送 `final`。断网或关闭浏览器后可刷新会话确认是否保存成功。进程中断遗留的执行状态在租约到期后的读取或发送时恢复为失败。

兼容接口 `POST /messages` 与 `/messages/stream` 支持 `question`、可选 `intent` 和 `history`（最多20条、完整问答对、20000字符），不使用持久检查点，也不保存草案；助手页使用会话接口。

## 工具与模型

- `search_documents(query)`：每轮最多3次，每次最多4段，复用现有文档检索。原文片段最多400字符。
- `read_task_board()`：每轮最多1次，最多完整读取100项；闲聊和文档问答不受看板数量限制。
- `generate_task_plan(goal)`：每轮最多1次，复用规划服务并返回经过校验的任务草案；工具内不保存草案、不创建任务、不提交审批。
- `check_requirements(scope)`：每轮最多1次，复用检查流程并显式指定检查用途，跳过二次分类；返回报告、检查范围和真实依据。
- `ChatCompletion`：结构化回答的数据结构。其他接口与离线演示通过 LangChain `ToolStrategy` 提交，不执行业务写入；MiMo 聊天不再向模型提供这个工具。

工具次数和最多5轮聊天模型调用由框架限制中间件管理，外层最多7次工具调用（包含非 MiMo 的最终格式工具）。每种业务能力调用后从本轮可选工具中移除，第5轮停止提供业务工具，要求模型结束回答。规划和检查内部调用受各自预算与助手总时限约束。摘要会额外调用配置模型，也受外层超时约束。

MiMo 官方接口（`live` 且地址主机为 `api.xiaomimimo.com`）会忽略 `tool_choice=required`，按 `auto` 选择工具，见[接口文档](https://mimo.mi.com/docs/zh-CN/api/chat/openai-api)。自动聊天直接使用 `auto`，提供当前可用的读取、规划与检查工具：有工具调用则执行并继续，没有工具调用则把自然语言正文作为最终回答。普通问答只需一次模型请求；业务操作按工具循环继续，不额外调用模型整理聊天 JSON。规划与检查的结构化输出继续严格校验，失败时返回错误，不把普通文字当作有效工件。

MiMo 的正文边生成边作为流式预览展示，后端校验通过并保存后才发送 `final`；无效回答清除预览，不提交到成功会话历史。空白、超长、被截断的回答以及无效工具调用仍会报错，不自动增加修复请求。升级前使用 `ChatCompletion` 的成功会话仍可继续。

MiMo 的返回格式由后端根据本轮执行记录组装：

- `answer` 保留模型正文；`basis` 表示是否实际查询项目工具。未查询显示「未查询项目资料」，不是对问题类型或事实正确性的判断。
- `sources` 从正文的 `[1]` 等编号提取、去重，并匹配本轮真实检索结果。代码、数组下标和 Markdown 行内链接的编号不作为资料引用。未知编号、跨轮沿用的编号被拒绝；仅查询文档且有命中时必须给出引用。
- `tasks` 展示本轮看板实际读取的任务记录，不猜测模型在正文中选择了哪些任务；未读看板则为空。
- `tool_calls` 来自真实执行记录；仅查询文档且没有命中时，`status=insufficient_evidence`。空看板表示已确认当前没有任务，仍可正常回答。

引用校验确认来源编号存在且属于本轮，不能证明每句话都被片段支持。自然语言模式也不能可靠推断“有命中但不足以回答”的语义状态；这类限制由模型在正文说明。涉及项目事实时必须先查询的要求保留在提示词中，后端不会把未查询的回答标为有项目资料依据。

工具身份来自服务端运行上下文，不属于模型参数。每轮读取器独立，引用和任务必须来自本轮工具结果，回答完成时复核数据是否变化。历史、摘要和旧工具结果只帮助理解追问，不代替当前项目事实。

回答包含 `answer`、`basis`、`sources`、`tasks`、`tool_calls`、`status`、`mode`、`artifacts`。旧记录省略 `artifacts` 时按空数组处理。服务器补齐真实文档与任务详情。无效引用、未知工具和额外身份参数被拒绝。流式增量只展示聊天正文和执行进度，工件完整结构在最终校验和保存成功后展示；失败则清除预览。

`artifacts` 用 `type` 区分两类结果：

- `task_plan`：包含 `goal`、规划 `result`、保存后的 `draft_id` 和 `draft_version`。每份工件保留自己的文档编号；卡片打开时按草案 ID 读取最新版本，编辑与送审检查版本号。
- `requirement_check`：包含检查 `result`，保留报告、依据和 `scope` 范围快照。检查服务本身仍只读，报告快照由聊天消息保存。历史报告不代表当前看板状态；「按缺口生成草案」生成新消息并重新读取项目资料。

工具只把工件概要交给聊天模型，不把工件编号合并到聊天正文的 `sources`。明确选择功能时，完成后把已验证回答与工件概要写入检查点，无额外聊天请求。正文里写“已生成草案”不会凭空产生草案卡片。

会话提交在短事务内锁定项目、任务和文档读取范围并复核基线，再一起保存草案和消息。失败或取消一起回滚，成功消息重试直接重放；最后成功的检查点编号才进入会话记录。自动生成仅保存草案，创建正式任务仍须走已有人工审批。

`live` 使用已有模型配置，MiMo 聊天需要工具调用能力，其他接口的聊天仍需要结构化输出能力；`mock` 使用离线演示模型，但经过同一 Agent、工具和检查点流程。演示模式只提供固定问候、真实检索及片段式摘要，不代表真实自然语言理解。原单轮 RAG、需求检查、任务规划和审批的结构化协议保持不变。

## 验证与升级

- `test_chat.py`：完整框架 Agent 的工具、权限、引用、预算和取消行为。
- `test_chat_model.py`：真实 SDK 配合本地 HTTP 替身，验证普通/流式协议及不完整 JSON。
- `test_chat_mimo.py`：MiMo 自动工具选择、单次自然语言回答和流式增量、引用校验、调用上限、取消、旧会话兼容与失败历史隔离。
- `test_chat_unified.py`：自动与明确用途的真实业务工件、身份与参数守卫、读取依据、调用限额、取消及资料变化。
- `test_chat_artifact_storage.py`：草案与消息原子保存、失败/取消回滚、幂等用途、编辑送审、报告恢复及旧数据迁移。
- `test_chat_sessions.py`：恢复、隔离、框架摘要、失败检查点、重试、接口和删除。
- `test_chat_sessions_postgres.py`：仅使用显式指定的独立 `chat_sessions_test` 数据库，验证真实 PostgreSQL 行锁、关闭连接后的检查点恢复、隔离和删除。
- 浏览器测试：恢复与切换会话、新会话隔离、删除、重试、引用、流式展示和移动端布局。

执行 `alembic upgrade head`，在 `0007_chat_sessions` 基础上应用 `0008_unified_assistant`，为消息新增 `intent`，旧消息默认 `auto`。工件快照使用原消息 JSON 列，草案使用现有 `plan_drafts`，无需新增工件表。应用启动时官方检查点组件执行 `setup()` 管理其检查点表；项目已有审批功能复用同一组件。Compose/Jenkins 会在启动服务前执行迁移，原有聊天、已保存草案和审批记录继续可用。

真实模型会收到当前会话历史/摘要和工具结果，不会加载其他会话的内容。部署仍沿用项目当前的单 API 实例要求；未为本功能引入新的服务或依赖包。
