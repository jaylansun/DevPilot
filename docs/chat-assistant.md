# 项目聊天助手

聊天使用一个输入框，真实模式下由模型决定直接回答，或先读取当前项目的文档、任务再回答。Agent 循环使用 LangChain `create_agent`，不另设意图分类模型。

## 会话上下文

每段聊天只使用自己的历史和摘要。点击「新对话」创建空上下文；「历史」可以继续或删除旧会话。刷新、重新登录、服务重启后仍可继续原会话。URL 的 `chat_session` 指定当前会话，未指定时加载当前项目最近更新的会话。会话列表每页50条，消息每页40轮，支持向前翻页。

不提取用户偏好或跨会话项目记忆，没有记忆设置、记忆面板、自动提取队列或“记住”写入指令。在一段会话中说过的信息可以用于这段会话的追问，新会话不会继承它。

- `chat_sessions` 保存业务会话信息、执行状态和最后成功的 `checkpoint_id`。
- `chat_messages` 保存原始问答、来源/任务快照和重试编号；一行代表一轮问答。
- LangGraph 官方 `AsyncPostgresSaver` 保存 Agent 上下文，线程标识为服务端生成的 `chat:{session_id}`，与审批线程隔离。身份和项目归属在读写检查点前校验，客户端不能提交检查点或历史。
- LangChain `SummarizationMiddleware` 在上下文达到30条消息或约8000 tokens时摘要较早的历史，配置保留最近20条消息；工具调用与工具结果也计入消息，框架会处理配对边界。摘要提示要求最多3000字符，框架不会将这个提示当作严格长度验证。原始问答表不受摘要影响。

下一轮显式从数据库记录的成功检查点继续。失败、取消、引用校验失败或答案保存失败时，框架可能已产生中间检查点，但这些检查点不会被下一轮采用。首次问答失败后的重试同样从空上下文开始。检查点缺失时可用原始成功问答重建上下文，再由框架处理摘要。

删除会话调用官方检查点删除 API，并删除原始消息和会话记录。回答尚未结束时删除返回409，避免并行写入重新产生上下文；停止或等待结束后可删除。

## 接口与执行状态

以下路径均以 `/api/v1/projects/{project_id}/chat` 为前缀，要求成员登录并验证项目归属。

| 接口 | 用途 |
| --- | --- |
| `GET`（前缀本身） | 模型配置、资料数量 |
| `GET /sessions?offset=0` / `POST /sessions` | 会话列表 / 新建会话 |
| `GET /sessions/{id}?before={seq}` / `DELETE /sessions/{id}` | 历史分页 / 删除会话与上下文 |
| `POST /sessions/{id}/messages` | 保存问答并返回完整 JSON |
| `POST /sessions/{id}/messages/stream` | 保存问答并返回 NDJSON v1、`kind=chat` |

发送参数仅为：

```json
{
  "question": "那我们项目有没有相关规则？",
  "client_message_id": "6b2426fb-5f73-46d3-b1a2-ae1fbb3a6412"
}
```

问题限1～2000字符。前端为新问题生成 UUID，重试复用同一编号。成功消息重试直接返回保存结果；同一编号更换问题返回409。每个会话同时处理一条消息，短事务中的会话行锁与120秒到期时间用于协调，模型等待期间不占用业务查询的数据库连接。失败或取消后可原位重试最后一条问题；开始其他问题后，旧的失败问题需要作为新消息发送。

Agent 调用预算100秒，完整会话处理105秒，流式边界115秒；提交最终答案和成功检查点后才发送 `final`。断网或关闭浏览器后可刷新会话确认是否保存成功。进程中断遗留的执行状态在到期后的读取或发送时恢复为失败。

兼容接口 `POST /messages` 与 `/messages/stream` 支持 `question` 和可选 `history`（最多20条、完整问答对、20000字符），不使用持久检查点；聊天页使用会话接口。

## 工具与模型

- `search_documents(query)`：每轮最多3次，每次最多4段，复用现有文档检索。原文片段最多400字符。
- `read_task_board()`：每轮最多1次，最多完整读取100项；闲聊和文档问答不受看板数量限制。
- `ChatCompletion`：通过 LangChain `ToolStrategy` 提交结构化回答，不执行业务写入。

工具次数和最多5轮聊天模型调用由框架限制中间件管理。模型最后一轮仅提供最终回答格式。摘要会额外调用配置模型，也受外层超时约束。

工具身份来自服务端运行上下文，不属于模型参数。每轮读取器独立，引用和任务必须来自本轮工具结果，回答完成时复核数据是否变化。历史、摘要和旧工具结果只帮助理解追问，不代替当前项目事实。

回答包含 `answer`、`basis`、`sources`、`tasks`、`tool_calls`、`status`、`mode`。服务器补齐真实文档与任务详情。无效引用、未知工具和额外身份参数被拒绝。流式增量只展示回答文字和固定进度，最终结果校验成功后展示引用；失败则清除预览。

`live` 使用已有模型配置，需要工具调用与结构化输出能力；`mock` 使用离线演示模型，但经过同一 Agent、工具和检查点流程。演示模式只提供固定问候、真实检索及片段式摘要，不代表真实自然语言理解。原单轮 RAG、需求检查、任务规划和审批入口继续保留。

## 验证与升级

- `test_chat.py`：完整框架 Agent 的工具、权限、引用、预算和取消行为。
- `test_chat_model.py`：真实 SDK 配合本地 HTTP 替身，验证普通/流式协议及不完整 JSON。
- `test_chat_sessions.py`：恢复、隔离、框架摘要、失败检查点、重试、接口和删除。
- `test_chat_sessions_postgres.py`：仅使用显式指定的独立 `chat_sessions_test` 数据库，验证真实 PostgreSQL 行锁、关闭连接后的检查点恢复、隔离和删除。
- 浏览器测试：恢复与切换会话、新会话隔离、删除、重试、引用、流式展示和移动端布局。

执行 `alembic upgrade head` 创建 `0007_chat_sessions` 的两张业务表。应用启动时官方检查点组件执行 `setup()` 管理其检查点表；项目已有审批功能复用同一组件。Compose/Jenkins 会在启动服务前执行迁移。此次迁移从 `0006_plan_drafts` 升级，不搬迁旧规划审批会话或浏览器临时历史。

真实模型会收到当前会话历史/摘要和工具结果，不会加载其他会话的内容。部署仍沿用项目当前的单 API 实例要求；未为本功能引入新的服务或依赖包。
