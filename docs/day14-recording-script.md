# DevPilot 完整演示录屏脚本

建议录制 8～12 分钟。真实模型和首次索引可能更慢，等待片段可剪辑；不要把模板演示描述成真实模型生成。

## 录制前准备

1. 按[部署说明](day14-deployment-demo.md)启动服务并初始化演示数据，确认 `restaurant.md` 已就绪，让模型缓存完成首次下载。
2. 准备两个独立浏览器窗口或浏览器上下文：成员 `demo14_member`、审批人 `demo14_reviewer`。输入自己设置的密码，录屏时遮挡密码输入过程，不展示 `.env`、Jenkins 凭据或令牌。
3. 选择模式：`live` 展示真实问答增量、需求检查与模型拆解；`mock` 展示完整系统链路并明确说明回答和草案为演示模板。
4. 打开 [restaurant.md](../service/demo/restaurant.md)；开始正式录制时创建一个新的项目，例如“餐厅外卖网站 · 录屏 01”。预置项目用于彩排，正式流程通过页面创建和上传，便于展示完整链路。

## 0:00～0:40：介绍与登录

**操作**：成员登录，展示项目列表。

**讲解**：“DevPilot 把项目资料、任务和 AI 协作放在一起。模型可以读资料、提出方案；真正写入任务前，需要另一位审批人确认。本次使用的是【真实模型 / 演示模板】模式。”

## 0:40～1:30：创建项目和已有任务

**操作**：创建项目，说明填写“顾客在线点餐、餐厅接单，重点完善订单校验和库存一致性”。进入任务页，手工创建两项任务：

| 标题 | 状态 | 优先级 |
| --- | --- | --- |
| 实现顾客登录与会话保持 | 已完成 | P2 |
| 实现菜品列表与分类筛选 | 进行中 | P2 |

**画面**：默认紧凑列表，演示状态筛选，再切到三列看板，然后回到列表。

**讲解**：“AI 规划前会读取这些已有任务，避免重新安排已经做过的工作。任务增多时在内容区滚动，导航不会被挤出屏幕。”

## 1:30～2:20：上传与索引

**操作**：进入知识库，上传 `service/demo/restaurant.md`，等待状态变成“已就绪”，显示片段数。

**讲解**：“服务器将 Markdown 切成片段，用本地中文向量模型生成索引。原文保存在 PostgreSQL，向量和模型缓存放在持久卷里。”

**核对**：不是只看到上传成功，要等索引就绪再提问。首次下载慢可暂停录制，字幕说明真实等待过程。

## 2:20～3:20：带引用的问答

**输入**：`下单前必须校验哪些信息？库存不足时怎么处理？`

**画面**：真实模式下文字逐步出现；完成后展开引用文件名，核对收货人、手机号、地址、库存和失败时保留输入。

**追问**：`最低起送金额是多少？`

**讲解**：“文档没有确定最低起送金额，助手应明确指出资料没有给出答案，不应编造数值。引用可以展开核对，不需要只相信模型的口头结论。”

**mock 说明**：只展示真实检索到的摘录及引用，不把摘录当成完整 AI 答案，也不模拟逐字输出。

## 3:20～4:10：需求检查

**输入**：`对照文档和已有任务，检查订单校验、重复提交和取消规则还有哪些遗漏或待确认项。`

**画面**：执行轨迹依次更新；真实模式下展示已有对应任务、可能遗漏、需要确认，展开实际读到的文档片段与任务范围。

**讲解**：“这里由 LangGraph 组织流程：判断用途，再读取文档和任务，最后生成并校验报告。报告会说明本次查了什么；检索到部分片段不等于检查过全部文档。”

**核对**：已接单后的取消规则应作为待确认项。已有任务不代表功能一定通过验收。mock 模式仅展示读取范围，不展示伪造的覆盖结论。

## 4:10～5:30：规划与提交审批

**输入目标**：`只规划下单前校验、重复请求保护与库存一致性，给出验收标准，不重复安排登录和菜品列表。`

**操作**：点“生成任务草案”，展示已保存的预览；点“编辑草案”，修改一个任务标题并“保存修改”，核对版本后点“提交这一版”。送审使用保存内容，不再次生成。

**讲解**：“预览是临时结果。提交审批会按当前目标重新生成并保存一份方案，可能与刚才预览不同。文档和看板工具只有读取权限，模型不能自行把任务写入数据库。”

**画面**：完成后显示“等待审批”；核对摘要、风险、任务验收标准和来源。刷新页面，再切回“审批记录”，查看同一记录。

## 5:30～7:00：审批与写入

**操作**：切换到审批人窗口，选择新提交的方案，展开任务和来源。点击“修改任务方案”，给一项任务的验收标准补充“重复提交返回同一订单编号，库存只扣减一次”，再点“修改后批准并加入看板”。

**讲解**：“审批决定由服务端保存，再通过 LangGraph 的 Command 恢复之前暂停的流程。任务只在确定性的写入节点中落库，数据库事务保证一批任务完整写入。”

**画面**：看到“已创建 N 项任务”；成员刷新任务列表，看到来源为 AI 的待办任务，打开标题检查刚才修改的验收标准。

**可选分支**：另提交一份方案并拒绝，核对任务数量没有增加。不要为了演示拒绝，误拒其他项目的真实方案。

## 7:00～8:30：重启与结束

**操作**：在专用演示环境中，保留一份待审批方案，再执行：

```bash
docker compose -f docker-compose.yml restart api
```

等 API 健康后刷新页面，确认已有任务、文档索引和待审记录仍在；审批人继续批准该待审方案。

**讲解**：“业务数据和 Checkpoint 在 PostgreSQL，索引在持久卷。进程重启后可以继续审批。后端对相同审批的重复执行返回原结果，不会重复创建同一批任务；这一点也有自动化测试验证。”

**结束语**：“这套项目跑通了资料检索、流式反馈、任务规划、人工审批和幂等写入。当前版本适合单实例学习和演示，不包含多人实时协作、PDF/OCR 或多 Agent。”

## 异常时如何讲解

- **模型超时**：展示保留的目标和请求编号；缩小范围后重试。已保存的中断记录使用“继续生成并提交”，不声称点击停止会撤销服务端已经保存的状态。
- **引用不足或结果不对**：展开实际来源，如实指出限制，不把错误回答剪辑成成功结果。
- **资料在审批前发生变化**：解释一致性校验，按提示重新规划；不要绕过冲突强制入库。
- **看不到审批入口**：成员在任务规划的“审批记录”中查看自己的记录，审批人登录后进入独立“审批工作区”。

录制完成后保存：视频文件、录制使用的模式/模型名称、Git 提交号和测试报告路径；不附带密钥或密码。
