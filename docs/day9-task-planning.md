# 第 9 天：只读 Agent 与任务规划草案

本文记录第 9 天功能。第 10 天已另增显式意图路由与需求检查入口，见 [需求缺口检查说明](day10-requirement-check.md)；原有规划功能仍保留。

## 新增了什么

项目详情增加“任务规划”入口。成员输入目标后，系统读取当前项目的资料和已有任务，返回方案摘要、假设、风险以及 1～12 个任务草案。每项包含标题、说明、优先级、验收标准、前置任务和资料引用。

本阶段只提供预览：不创建任务、不审批、不保存方案，也不新增数据库表或迁移。返回值的 `persisted` 固定为 `false`。刷新页面、清空草案、重新生成或离开规划页都会清除旧结果。

仍通过“AI 问答”和“任务规划”两个入口选择用途，没有加入意图路由。原有知识库问答流程不变。

## 如何体验

1. 登录成员账号，打开自己的项目。
2. 在“知识库”上传需求文档，等待状态变为就绪。索引失败时先解决向量模型下载或网络问题。
3. 打开“任务规划”，输入有具体范围的目标，例如“根据文档拆分购物车和下单功能”。
4. 点击生成，核对草案中的任务、依赖关系和验收标准。展开引用，检查原文是否真的支持相应建议。
5. 如需更改范围，修改目标后重新生成。当前不提供提交审批或批量写入按钮。

模型配置沿用第 8 天的 `AI_MODE`、`MODEL_NAME`、`LLM_BASE_URL`、`LLM_API_KEY`，不增加新的密钥。

- `AI_MODE=mock`：仍进行真实文档检索和看板读取，但用固定三步模板展示草案结构，不调用聊天模型，也不代表已经完成真实需求分析。本地向量模型首次使用仍可能需要下载。
- `AI_MODE=live`：模型通过工具读取资料和看板，再返回结构化方案。目标、检索片段和读取到的任务内容会发送给配置的模型服务，请先确认资料可向该服务提供，并考虑模型费用。

在 `live` 模式下，`configured=true` 仅表示必要配置非空，不证明网络、密钥或模型工具调用能力可用；`mock` 不要求这三个模型配置，因此直接返回 `true`。真实供应商需要支持工具调用，并单独验证兼容性；目前的自动化验收使用离线模拟模型，没有进行真实模型调用或效果评估。

## 后端如何工作

请求体只有 `goal`，长度 1～2000 字符。后端从 JWT 获取用户身份，结合路由中的项目 ID 检查归属；模型不能指定另一个用户或项目。

`PlanService` 先检查权限、就绪文档和模型配置，再为本次请求创建独立的 `PlanningReadService`。服务端把身份和读取器放进 `PlanToolContext`，通过 `ToolRuntime` 注入工具。身份上下文不会作为模型可填写的工具参数暴露。

真实模式使用 LangChain `create_agent`，只注册两个只读工具：

- `search_documents(query)`：使用已有的本地 BGE 与 Chroma 检索当前项目的就绪文档；单次最多 4 段，整次规划最多保留 12 段。同一片段在多次检索中复用同一个来源编号。每段正文和标题各保留前 400 字符，并向工具调用方标记截断；前端展开的是这些摘录，不是完整文档。
- `read_task_board()`：读取当前项目全部任务，以便规划时参考现有工作并检查重复标题。最多支持 100 个任务；超过时明确拒绝，不把被截断的看板说成完整数据。任务标题完整保留，说明与验收标准各截取前 400 字符并标记截断。

工具没有创建、更新、删除、任意 SQL 或执行命令的能力。每次读取使用独立数据库会话；同一次规划的工具读取串行处理，避免并发共享会话。每次读取都会重新检查项目权限。

模型使用 `ToolStrategy(PlanProposalVO)` 输出结构化方案，不手工从 Markdown 中截取 JSON。服务端随后检查：

- 两个只读工具确实被执行，且有实际检索来源；
- 任务数为 1～12，优先级为整数 1～5，标题、说明和验收标准非空；
- 草案 ID 唯一，依赖引用存在，没有自我依赖和循环依赖；
- 草案标题去除首尾空白、合并空白并忽略大小写后不重复，也不与当前看板同名；
- 至少一个任务引用资料，所有引用编号都来自本次实际检索；
- 输出前再次读取并比较项目、任务与就绪文档状态，发现规划期间数据变化就返回 409，要求重新生成。

这些是权限、结构与一致性检查，不保证任务拆解完整，也不保证原文支持模型的每个结论；同义但不同标题的重复任务仍需人工判断。最后一次复核也不是持久锁，返回后项目仍可能发生变化，因此本阶段不直接执行草案。

用户目标、资料和已有任务都按不可信内容处理，不能用其中的指令改变工具权限。前端按普通文本渲染结果，不执行模型返回的 HTML。

## 调用上限与失败处理

- 每个服务实例同时生成 1 个规划，获取名额最多等待 1 秒，繁忙时返回 503。
- 规划处理限时 65 秒，前端请求上限 75 秒；模型单次请求限时 25 秒且不自行重试。
- 最多 4 次模型调用、6 次工具调用额度。结构化方案输出也占一次工具额度，因此成功返回方案最多可使用 5 次读取调用。
- 仅超时、连接失败和 HTTP 传输类工具异常最多重试 1 次。一次逻辑工具调用最多尝试 2 次；这些实际尝试仍受整体超时约束。权限、业务校验失败不重试。
- 无就绪文档或无相关片段时，提示补充资料；数据变化时要求重新规划；格式、引用或调用限制不满足时返回中文错误，不展示伪造的成功结果。

页面可“取消等待”，并忽略迟到的返回值。这不承诺立即终止服务端请求、向量计算线程或供应商已开始的推理，也不承诺退还已产生的费用。服务端仍受其超时与调用上限约束。

工具调用列表是请求结束后的读取记录，不是实时进度或流式消息。

## 主要文件职责

后端路径相对于 `service/`：

| 文件 | 作用 |
| --- | --- |
| `app/api/v1/plan_controller.py` | 规划状态和生成草案接口，接入身份依赖 |
| `app/schemas/plan_qo.py` | 校验输入目标，拒绝额外身份或执行字段 |
| `app/schemas/plan_vo.py` | 草案、任务、来源与工具记录结构，校验数量、重复与依赖 |
| `app/services/plan_service.py` | 权限、配置、并发与超时，以及模型结果复核 |
| `app/services/plan_agent_service.py` | 只读 Agent、提示词、结构化输出、调用限制及演示模板 |
| `app/services/planning_read_service.py` | 有权限隔离的资料与看板读取、来源编号、数据变化检查 |
| `app/tools/planning_tools.py` | 两个只读工具和服务端注入的运行时上下文 |
| `app/main.py`、`app/api/v1/__init__.py` | 服务初始化与路由注册 |
| `pyproject.toml`、`uv.lock` | 新增 LangChain 并锁定依赖；LangGraph 作为 Agent 的依赖安装 |
| `tests/test_plan_*.py`、`tests/test_planning_tools.py` | 接口权限、草案约束、真实 Agent 框架离线测试、工具与服务边界 |

前端路径相对于 `vue/`：

| 文件 | 作用 |
| --- | --- |
| `src/api/planning_api.ts` | 状态与生成请求、超时与取消信号 |
| `src/components/TaskPlanning.vue` | 目标输入、草案预览、来源展开、取消等待和失败提示 |
| `src/views/ProjectDetailView.vue` | 项目内“任务规划”入口与标签路由 |
| `src/layouts/AppLayout.vue` | 对应的工作区面包屑 |
| `src/types/api.generated.ts`、`src/types/api.ts` | 从后端生成的类型及前端别名 |
| `tests/e2e/task_planning.spec.ts` | 用测试 API 验证草案、依赖、引用、取消、失败和手机布局 |

## 验证与部署

后端测试使用隔离测试数据库或模拟读取器；Agent 测试使用真实 LangChain 工具调用流程加离线模拟聊天模型。前端浏览器测试使用 API 替身，不修改真实项目，也不验证真实模型输出质量。

任务规划不需要新增数据库迁移，新的 Python 依赖已经写入锁文件。Jenkins 的部署流程仍使用原来的 `devpilot-env-file` 凭据；后端测试阶段单独使用假配置和禁网容器，不再读取部署 `.env`，避免真实模型配置干扰测试或密钥出现在失败日志里。修复测试隔离不修改真实 `.env` 或 Jenkins 凭据。

本地代码不会因点击 Jenkins 构建而自动上传：先将需要部署的代码和锁文件提交、推送到 Jenkins 使用的分支，再手动点击构建；仅本地存在的未提交文件不会被 Jenkins 从 GitHub 拉取。不要提交 `.env`。模型配置如有变化，单独更新 Jenkins 的 `devpilot-env-file` Secret file 后再部署。

框架机制参考官方的 [工具与运行时上下文](https://docs.langchain.com/oss/python/langchain/tools)、[结构化输出](https://docs.langchain.com/oss/python/langchain/structured-output) 和 [内置中间件](https://docs.langchain.com/oss/python/langchain/middleware/built-in)。实际项目行为以本仓库代码和测试为准。
