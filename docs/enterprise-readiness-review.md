# DevPilot 上线与工程化检查

检查日期：2026-09-23。范围为当前工作区，包括尚未提交的部署调整。

以小团队真实上线、持续交付、权限控制与数据可靠性为基准。当前功能链路完整，但还有需要在正式使用前补齐的可靠性和运维能力。现有 FastAPI、Vue、PostgreSQL、LangGraph 架构可以继续使用。

本次检查包含核心代码阅读、选定回归测试、事务生命周期隔离验证，以及 npm 依赖审计；没有修改业务代码或部署配置，没有对运行中的业务环境进行故障注入或压力测试。

## 已有基础

- 服务端校验成员身份和项目归属，模型不能指定工具的用户与项目身份。
- AI 工具只读，审批决定落库后才允许创建任务；任务与审批执行结果在同一事务提交。
- 审批使用稳定任务 ID、唯一约束和重复决定检查，任务编辑使用版本号处理冲突。
- 请求、结构化模型结果和引用来源经过校验；Markdown 禁用原始 HTML、图片和危险链接。
- 流式事件使用显式 EventPublisher 接口、有界队列、超时和取消清理。
- 已有数据库迁移、依赖锁文件、前后端测试、真实 PostgreSQL 恢复测试和浏览器验收脚本。

## 优先修复

### R01：普通写接口可能先返回成功，再提交数据库事务

**优先级：P1。已做隔离复现。**

[数据库依赖](../service/app/database.py)的 `get_db_session()` 在 `session.begin()` 内 `yield`，退出依赖时才提交；[接口依赖](../service/app/api/dependencies.py)使用默认的请求作用域。当前 FastAPI 版本为 0.141.1，默认在响应发送完后清理这类依赖。

使用项目现有依赖、假会话和真实 FastAPI ASGI 生命周期验证，事件顺序是：

```text
正常：接口返回 → 发送 201 → 响应结束 → 尝试提交 → 提交成功
失败：接口返回 → 发送 201 → 响应结束 → 尝试提交 → 回滚
```

这会影响依赖该机制提交的普通项目、任务等写接口：提交阶段失败时，客户端可能已经收到成功。审批核心写入已有显式事务边界，不应把此结论扩展到所有写操作。

**修改方向：** 普通写操作在返回成功前完成事务提交，可采用明确的服务层事务边界，或独立的函数作用域事务依赖。`flush()` 不等于提交。

**验收：** 注入提交失败，客户端必须收到错误，数据库没有新增数据；正常响应只能在提交成功后发出。

### R02：模型等待和流式发送期间持有数据库连接

**优先级：P1。代码路径确认，容量影响尚未压测。**

[问答接口](../service/app/api/v1/rag_controller.py)、[规划接口](../service/app/api/v1/plan_controller.py)等将请求级 Session 传入流式操作。鉴权查询与业务查询开启的事务，会随响应持续到流结束。连接池配置为 5 个常驻连接、最多 10 个额外连接；规划业务预算为 120 秒。

**修改方向：** 鉴权与业务读取使用短会话，只在数据库访问期间占用连接；模型调用和事件发送不持有数据库事务。流中需要再次读取时新建短会话，保留现有资料变化检查。不能只把所有依赖改为 `scope="function"`，否则流还可能使用已退出事务的 Session。

**验收：** 模拟慢模型、慢客户端和主动断开，观察连接及时归还，普通 CRUD 不被流式请求长期阻塞。

FastAPI 对默认依赖作用域与流式响应生命周期的说明见[官方文档](https://fastapi.tiangolo.com/advanced/advanced-dependencies/)。

### R03：登录缺少限流，账号缺少停用与令牌吊销能力

**优先级：P1，扩大访问范围前完成。**

[登录接口](../service/app/api/v1/auth_controller.py)没有账号/IP 失败次数控制；[用户模型](../service/app/models/user_do.py)没有停用状态或会话版本。[令牌验证](../service/app/security/tokens.py)校验签名和过期时间，但没有主动吊销机制。退出登录目前清理浏览器存储。

**修改方向：** 增加按账号与可信来源 IP 的限流、渐进冷却和 429 响应；补账号停用、受控密码重置、令牌版本或会话撤销机制；生产配置启动时校验 JWT 密钥强度。不存在的用户可执行等价密码校验，减少账号存在性时间差。企业统一登录有明确需求时再接 OIDC/SSO。

单进程阶段可采用简单限流方案；多实例时计数必须共享。不要依靠无限期锁号防暴力猜测，以免被用于恶意锁号。

**验收：** 连续失败触发限制，合法用户可恢复；停用账号或撤销会话后，旧令牌无法继续使用。设计依据见 [OWASP 认证建议](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

### R04：健康检查不能反映业务是否可用

**优先级：P1。**

[健康接口](../service/app/main.py)固定返回 `status="ok"`，没有访问数据库。[Compose](../docker-compose.yml)与 [Jenkins](../Jenkinsfile)据此判断 API 健康，数据库运行中断开后仍可能通过检查。

**修改方向：** 区分进程存活检查与可接流量检查。后者以短超时验证数据库和必要的本地存储；索引工作进程状态、模型配置等另行报告。不要每次探针都付费调用大模型，也不要因为外部模型波动反复重启整个 API。

**验收：** 在隔离环境停止数据库，可用性探针返回 503；恢复后自动恢复。存活探针保持轻量。

### R05：删除项目后，工作流检查点没有对应清理

**优先级：P1，涉及真实项目资料时完成。**

[项目删除](../service/app/services/project_service.py)会级联删除业务记录并写入向量清理任务，但没有记录或清理 Conversation 对应的 `thread_id`。LangGraph 检查点独立保存，不与业务表外键级联；[审批状态](../service/app/services/approval_graph.py)包含目标、方案及资料片段。因此业务项目删除后，历史内容仍可能留在检查点表。

**修改方向：** 明确审批记录与检查点的保留周期。需要删除时，在删除业务记录前，将 thread ID 写入持久清理任务；由后台调用 Checkpointer 的 `adelete_thread()`，支持失败重试，并协调仍在运行的流程，防止清理后重新写入。已有向量清理模式可复用设计思路。

**验收：** 项目删除和进程重启后，清理任务仍能完成；检查点、写入片段及向量符合保留策略，不留下无法归属的历史数据。

### R06：备份、恢复与发布回滚尚未形成流程

**优先级：P1，承载真实业务数据前完成。**

仓库已有命名卷和重启恢复验证，但未找到定时备份、异机备份、恢复演练或发布回滚工具。[Jenkins](../Jenkinsfile)直接构建并替换运行容器；[API Dockerfile](../service/Dockerfile)在启动时执行迁移。

**修改方向：** 为 PostgreSQL（包括检查点）建立备份和保留策略，验证 Chroma 的恢复或从原文重建流程。先明确允许丢失多久的数据、允许恢复多久，再选择定期备份或 WAL 时间点恢复。发布镜像按提交 SHA 标记并保留上一版，迁移独立执行且兼容前后版本；失败时能回滚应用。数据库迁移不能简单假定可随镜像一起倒退。

**验收：** 在全新隔离环境从备份恢复项目、文档、待审批记录和已创建任务；演练部署失败回滚，并记录恢复耗时。数据库恢复机制见 [PostgreSQL 官方文档](https://www.postgresql.org/docs/17/continuous-archiving.html)。

### R07：运行权限和 CI 凭据边界需要收紧

**优先级：P1，部署到共享主机或扩大网络访问前完成。**

[API 镜像](../service/Dockerfile)没有切换非 root 用户。[配置初始化](../scripts/init_env.py)让运行服务与数据库初始化使用同一账号，需要拆分权限。[Jenkins 配置](../docker-compose.yml)将 8080 发布到所有网卡，并挂载宿主机 Docker socket；流水线在测试前就将部署凭据复制到工作区。

**修改方向：** API 改用非 root 用户并明确数据目录权限；拆分数据库初始化/迁移账号与业务账号；配置独立部署凭据，在部署阶段才提供。Jenkins 限制管理入口访问，隔离构建与部署执行环境，不让不可信分支访问部署凭据或生产 Docker socket。跨机器访问应用时补 HTTPS 和合适的安全响应头。

**验收：** 业务账号不能修改数据库结构；API 非 root 运行仍可正常索引；普通验证任务不能读取部署凭据或操作业务容器。

## 随工程化补齐

### R08：现有关键验收还没有全部进入发布门禁

**优先级：P2；生产发布前应纳入。**

[真实 PostgreSQL 测试](../service/tests/test_approvals_postgres.py)在缺少专用连接时跳过；现有 Jenkins 后端测试禁网且未配置该连接。项目已有[完整验收脚本](../scripts/test_day13.py)和浏览器用例，但流水线没有执行完整验收。

建议在独立 CI 网络内启动临时 PostgreSQL，将迁移、审批事务回滚、重启恢复和关键浏览器用例纳入必过检查；保留现有禁网单元测试层。增加提交时机、并发、连接池、检查点清理的回归，以及统一格式、类型检查和依赖扫描。

### R09：补充可定位故障的日志、指标与审计记录

**优先级：P2。**

目前有 Request ID 和错误日志，但[流式执行](../service/app/services/run_stream_service.py)及部分模型服务仅记录异常类型，没有统一关联请求、用户、会话和阶段耗时。审批记录已经保存决定，不等于所有关键操作都有审计记录。

建议统一结构化日志，记录请求/运行标识、错误码、耗时和经脱敏的异常位置；统计模型延迟、失败率、Token 用量、连接池占用、索引积压及审批恢复失败；关键账号、删除和审批操作记录操作者与时间。按需要接 OpenTelemetry、指标系统和告警，避免默认采集密钥、完整文档和模型提示内容。

### R10：解决索引阻塞检索，并在扩容前移除进程内协调假设

**优先级：P2；增加 API 实例前必须处理。**

[索引服务](../service/app/services/document_index_service.py)在整份文档向量化期间持有与在线检索共用的 RLock。上传大文档时，其他项目检索也会等待。[索引工作进程](../service/app/services/document_worker_service.py)随 API 启动，恢复逻辑会把所有 indexing 状态改回 queued；[审批锁](../service/app/services/approval_service.py)只在进程内生效。各 AI 服务还各有一个固定并发名额。

建议先测量索引与查询延迟，缩小共享锁范围或分离索引与查询执行资源；将索引工作进程独立部署并增加任务认领、租约与超时恢复。多实例前使用共享的任务协调与流程锁，并确定向量服务的并发访问方案。可继续使用 PostgreSQL 任务表，不必立即引入 Redis/Celery；如采用外部队列，再评估运维成本。

### R11：团队权限与 AI 成本治理按使用范围扩展

**优先级：P2/P3，取决于是否多人协作和多组织部署。**

当前项目只有 owner，角色只有 member/reviewer；审批人可查看全部已提交方案，这是现有产品规则。若要支持多个团队，应增加组织、项目成员与审批人分配范围，避免不同组织共用全局审批权限。需要对应的租户隔离回归测试。

模型调用已有超时、调用次数和输出长度限制；建议再增加按用户/项目的配额与费用记录、模型和提示版本、固定质量评估集。评估集覆盖无依据拒答、错误引用、提示注入、重复任务和审批边界；对真实模型质量单独验收。

### R12：升级有公告的测试依赖，并建立持续扫描

**优先级：P2。**

本次 npm audit 返回 2 个 moderate 包记录，均对应同一公告：`vitest` 与 `@vitest/mocker` 的路径穿越/文件读取问题。公告明确其利用依赖开发服务器和相关插件暴露条件；不据此认定部署后的 Nginx 静态站点存在同等漏洞。

建议升级到公告修复且与项目兼容的受支持版本，验证单元与浏览器测试，并在 CI 中加入前端、Python 依赖和容器镜像扫描。不要直接运行可能引入未经验证大版本变化的强制自动修复。

依据：[Vitest 官方安全公告](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9)。本次没有完成 Python 和容器镜像漏洞扫描。

## 实施顺序

1. **事务与可靠性：** R01、R02、R04，先解决成功响应时机、长事务和健康误判，补针对性测试。
2. **安全与数据生命周期：** R03、R05、R06、R07，补账号控制、清理、备份恢复和部署权限。
3. **持续交付与运维：** R08、R09、R12，将集成验收、日志指标和依赖治理纳入日常流程。
4. **按容量和组织需求扩展：** R10、R11，先测量，再决定是否引入独立向量服务、Redis、任务队列或组织权限模型。

目前优先保持模块化单体。没有证据表明需要引入微服务、Kubernetes、Kafka、Elasticsearch，或把所有辅助函数改成类。
