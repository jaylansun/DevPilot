# 网页自由改造插件开发计划

本计划用于开发一个浏览器插件：用户通过自然语言或点选网页区域，调整第三方网站的布局、样式和信息顺序，在原网站上预览、继续修改、保存和撤销。淘宝电脑版是首个验证场景，产品目标是形成可复用的网页改造能力。

计划日期为 2026 年 9 月 30 日。当前已完成产品讨论和交互示意，尚未开发真实扩展，也未验证真实淘宝页面的改造兼容性。文档中的时间、预算和通过条件均为开发估算或拟定标准，不能作为已经达到的结果。

当前仓库是已有的 DevPilot 项目，本文件仅作为新项目计划存放在其文档目录。实施时建议建立独立项目目录或仓库，独立管理扩展权限、依赖、数据库和部署配置。

## 产品目标与使用流程

核心体验是：打开原网站，在插件侧边栏描述修改要求，直接在原网页上预览效果，继续调整后保存。关闭侧边栏可以继续浏览；再次访问匹配的页面时，已保存方案由本地程序重新应用。

典型要求包括：

- 改成三栏，左边商品图片，中间介绍和评价，右边规格与购买。
- 图片区域加宽，介绍区域缩窄。
- 把评价放到商品介绍前面。
- 在已修改的页面上继续要求购买区域改放左边。
- 将某个推广区域折叠，并保留展开入口。

用户仍然访问原网址，商品数据、登录状态和业务操作仍由原网站提供。多数布局修改优先作用于原元素；需要重新设计控件时，再建立新控件与原控件的对应关系。

目标是自由组合布局和样式。实际可用范围受网页结构、原网站框架、跨域框架、封闭组件和程序操作限制影响。产品必须明确显示已经验证的能力和无法执行的修改，不能承诺所有网站的所有区域都可以任意重排。

## 技术选择与用途

依赖版本在项目初始化时依据兼容性验证后锁定，提交锁文件。开发过程中按需要升级，避免每次安装自动改变整套依赖。

| 技术 | 用途 | 使用意义 |
| --- | --- | --- |
| WXT | 扩展工程组织、开发、构建、打包 | 统一侧边栏、网页脚本和后台入口，减少扩展工程配置工作 |
| TypeScript | 浏览器端逻辑和消息契约 | 明确页面身份、目标元素、方案版本和执行结果的类型 |
| Manifest V3 | Chrome 扩展运行规范 | 按浏览器要求声明权限、脚本和后台能力 |
| Vue3 | 侧边栏、方案历史、编辑控件 | 复用已有经验，快速完成可持续修改的交互界面 |
| Shadow DOM | 插入原网页的浮窗或新控件 | 减少网页样式与插件界面的相互影响；浏览器侧边栏本身无需依赖它 |
| DOM 和 CSS Grid 与 Flexbox | 读取元素、应用布局和样式 | 实际执行用户的网页改造要求 |
| MutationObserver 和 ResizeObserver | 观察页面结构和元素尺寸变化 | 在节点替换或布局变化后检查目标绑定，而非持续全页扫描 |
| Python 和 FastAPI | 任务、反馈、方案接口 | 接入 AI 工作流和持久化服务，开发成本符合现有经验 |
| Pydantic 和 JSON Schema | 修改方案与接口契约 | 验证 AI 输出格式并保持前后端约定一致 |
| Ajv 预编译校验器 | 浏览器收到方案后的格式检查 | 在构建期生成校验代码并随扩展打包，避免运行时动态编译 |
| LangGraph | 生成、检查、预览反馈、修正流程 | 管理有分支、等待和恢复的 AI 任务 |
| 多模态模型 | 理解截图、网页结构和用户要求 | 同时判断视觉位置与可操作元素，模型供应商根据评测选择 |
| SSE | 推送进度和解释文本 | 让用户了解任务进展；方案完整且检查通过后才执行 |
| chrome.storage.local | 当前设备的启用方案和设置 | 页面再次访问时可以在本地应用方案 |
| PostgreSQL | 任务、版本、事件、检查点 | 支持任务恢复、执行记录和并发版本检查 |
| SQLAlchemy 和 Alembic | 数据访问与迁移 | 管理短事务、数据库结构变化和升级过程 |
| Playwright 和 Chromium | 扩展浏览器回归 | 验证布局、原交互、页面更新和撤销 |
| Vitest 和 pytest | 关键逻辑测试 | 验证目标匹配、方案校验、任务状态和版本冲突 |
| Docker Compose | 个人后端部署 | 一次启动 API、Worker 和数据库，降低环境差异 |

WXT 的网页脚本和 UI 工具见 [WXT 文档](https://wxt.dev/guide/essentials/content-scripts)。Shadow DOM 主要提供界面封装，不作为不可信代码的安全沙箱。

浏览器网页脚本可以读取和修改 DOM，但与网页脚本的变量环境存在隔离；不能默认直接读取网站内部框架状态。[Chrome Content Scripts 文档](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

## 架构与模块边界

```text
Chrome 扩展
  Vue3 侧边栏
    描述要求  查看进度  对比方案  保存与撤销
      |
  扩展后台
    标签页协调  消息转发  权限与生命周期处理
      |
  网页脚本
    收集相关区域  定位目标  应用方案  检查结果
    观察更新  重新绑定  原控件同步  撤销
      |
  本地方案存储

HTTPS 或本机受控 HTTP 接口
      |
FastAPI
  创建任务  接收浏览器反馈  查询进度  管理方案版本
      |
Python Worker 与 LangGraph
  分析  生成  校验  等待预览  修正  完成
      |
PostgreSQL
  任务  事件  方案版本  检查点  Worker 租约
      |
配置的模型服务
```

浏览器修改状态与后端 AI 任务状态分别管理。后端完成生成，不代表浏览器已应用，更不代表用户已经保存；服务端和侧边栏必须根据浏览器执行回执区分这些结果。

| 状态归属 | 初始状态约定 | 转移依据 |
| --- | --- | --- |
| 后端任务 | queued、running、awaiting_feedback、completed、failed、cancelled、expired | 持久任务状态与有效浏览器回执；completed 表示候选方案通过检查，不代表用户已保存 |
| 浏览器改造 | original、applying、previewing、saved、suspended、reverting | 当前页面身份、实际应用结果和用户操作；暂停时说明失效区域，撤销完成后回到 original |

进入 awaiting_feedback 后保存检查点并释放 Worker 的执行租约，反馈或超时再触发下一步。浏览器预览过程中页面已变化，则废弃候选方案并重新收集证据。两端状态之间用带版本的事件联系，不靠一个共享的“完成”字段推测页面结果。

扩展后台可能被浏览器休眠或重启，因此不把它的内存当作任务真相来源。侧边栏、网页脚本和持久存储共同支持重新连接；服务端任务有独立持久状态。[Chrome 后台生命周期说明](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

## 改造方案的数据契约

AI 返回配置数据，插件内置执行逻辑。普通模式不包含 JavaScript 字符串、循环、任意表达式、网络请求或通用脚本解释器。

下面是结构示例，区域编号是快照中的引用，不是淘宝提供的接口。

```json
{
  "schemaVersion": 1,
  "baseRevision": 2,
  "pageContext": {
    "documentToken": "document-example",
    "routeVersion": 1,
    "snapshotId": "snapshot-example"
  },
  "layout": {
    "containerRef": "region-main",
    "mode": "grid",
    "columns": ["35%", "40%", "25%"],
    "gapPx": 20,
    "placements": [
      {"regionRef": "region-gallery", "column": 1},
      {"regionRef": "region-description", "column": 2},
      {"regionRef": "region-purchase", "column": 3}
    ]
  },
  "appearance": {
    "region-purchase": {
      "fontSizePx": 14,
      "paddingPx": 12
    }
  }
}
```

示例列宽是比例意图。执行器扣除间距后转换成适当的比例轨道，不能直接把总和为 100% 的列宽加上间距，导致横向溢出。

| 契约 | 关键字段 | 用途 |
| --- | --- | --- |
| PageContext | tabId、frameId、documentToken、routeVersion、URL、pageType | 绑定当前标签页、文档和页面路由 |
| PageSnapshot | snapshotId、时间、相关区域、元素特征、尺寸、可选截图 | AI 生成时的网页证据 |
| TargetDescriptor | 本次 regionRef、标签、角色、属性、邻近文字、结构特征 | 本次定位和后续重新绑定 |
| ModificationPlan | schemaVersion、baseRevision、布局、样式、折叠、有限组件配置 | 明确改哪些区域以及如何呈现 |
| ValidationReport | 格式检查、目标匹配、遮挡、溢出、缺失区域、执行结果 | 决定能否展示和修正 |
| SavedRecipe | 方案版本、匹配范围、持久定位描述、兼容性证据、启用状态 | 刷新后和同类页面上重新应用 |
| ActionBinding | 新控件、原目标、动作类型、成功条件、超时 | 连接新控件与原网站操作 |

regionRef 只在某次快照中有意义。保存方案时转换为持久 TargetDescriptor，禁止将旧 DOM 对象、旧元素编号直接用于新页面。

Pydantic 为契约定义的主要入口，导出统一 JSON Schema。浏览器端生成 TypeScript 类型并使用相同 schema 对应的预编译校验器。语义检查另行实现，不能把格式校验视为功能正确。[Ajv 预编译说明](https://ajv.js.org/standalone.html)

## 页面身份与方案匹配

页面身份分成访问范围和当前运行实例。访问范围回答方案适用于什么页面；运行实例回答一次异步结果能否应用在眼前的页面。

| 层次 | 设计 |
| --- | --- |
| 当前页面 | 规范化后的站点、路径和关键参数，对应具体商品或文章 |
| 同类页面 | 站点、页面类型、经过验证的目标区域特征 |
| 当前运行实例 | 标签页、框架、文档 token 和路由版本 |
| 修改版本 | baseRevision 与新 revision，防止迟到修改覆盖后续修改 |

仅忽略已确认不影响页面身份的追踪参数，不能默认删除所有查询参数。商品 ID、搜索条件等可能改变页面内容。

第一版同一页面只启用一套布局方案，连续修改产生新版本。当前页面规则优先于同类规则，用户可以明确切换版本。多套方案叠加和冲突合并放到后续版本。

页面切换或主要内容切换后递增运行版本，废弃旧快照和待执行动作。相同 URL 下内容变化也需要识别，不能只依赖地址栏变化。

## 元素定位与动态页面处理

定位器结合标签、可访问角色、属性、邻近文字、区域关系和结构特征寻找候选。CSS selector 可以作为线索，但不把长层级路径或随机 class 当作唯一长期依据。

每次应用前检查候选数量、区域用途、可见性和上下文。多个候选无法区分时，允许用户点选确认或要求重新识别。引擎匹配分数与 AI 自述的置信度分开记录。

MutationObserver 监听相关区域的结构、文字和属性变化，ResizeObserver 监听目标尺寸变化。表单属性值等状态还要结合 input、change 等事件和操作后的读取，不能假定 DOM 观察器能捕获一切变化。[MutationObserver 文档](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver)、[ResizeObserver 文档](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)

更新策略为：合并短时间内的通知，局部重新检查，只在目标确实被替换时重新绑定。标记自己的修改，避免观察到自己写入后反复执行。每个观察器和监听器都必须有清理入口。

小变化可以在检查通过后重绑；主要结构改变则暂停受影响操作。修复流程重新取得快照并生成候选方案，自动检查通过后才提供新的预览。

## 布局执行与撤销规则

改造引擎优先修改现有布局属性，保留原元素及其事件链。跨父容器重排需要先判断现有结构是否能够通过布局样式实现；不能实现时，进入受控结构实验或报告当前不支持。

直接移动节点可能影响框架更新、事件委托、焦点和弹层定位，不能以初次显示正常作为通过依据。[React 的 DOM 操作说明](https://react.dev/learn/manipulating-the-dom-with-refs#best-practices-for-dom-manipulation-with-refs)

每次应用按照以下顺序执行：

1. 检查页面身份、方案基准版本和全部目标。
2. 形成局部变更集合，登记引擎拥有的样式、属性、组件与监听器。
3. 应用修改并检查布局，失败时撤回该次变更。
4. 提交本地预览版本，再发送执行回执。
5. 用户保存后更新启用方案及本地版本。

优先通过带唯一标识的样式表管理布局，撤销时删除自己的样式表。必须修改原属性时记录原值和自己写入的值；若原网站之后已写入新值，不能无条件恢复旧值。

撤销移除插件改造，保留网站自身最新的商品数据和选中状态。不能用旧页面 HTML、截图或 clone 替换整页。复杂结构修改无法可靠局部恢复时，停用方案后通过刷新恢复原页面，并清楚展示恢复方式。

CSS 视觉重排还需要检查键盘焦点和阅读顺序。出现严重顺序错乱的方案不能仅凭外观正确通过验收。

## AI 工作流与浏览器反馈

AI 处理用户意图、相关区域识别、布局设计、继续修改和修复。浏览器本地程序处理目标检查、实际应用、普通重绑和原网站状态同步。

```text
读取请求与当前方案
  -> 检查页面快照
  -> 理解意图与引用区域
  -> 生成候选方案
  -> 格式与语义检查
  -> 等待浏览器检查和预览回执
  -> 检查通过则完成
  -> 检查失败且有预算则修正
  -> 超过预算则失败并保留可恢复状态
```

继续修改以当前完整方案和 revision 为基准。模型先输出修改意图，服务端确定性合并并校验完整新方案。用户要求只改购买区域时，其他区域配置必须在验收中检查保持一致。

LangGraph 保存阶段状态和检查点。它的检查点不自动提供任务队列、跨进程调度或浏览器连接，这些由 Worker 和数据库任务管理实现。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

模型供应商先通过固定任务对比再选定。评测关注定位、方案正确性、修正能力、耗时和成本，不只评价回答文字是否流畅。统一模型适配层，避免业务逻辑依赖单个供应商响应格式。

下面是待实测调整的初始预算：

| 配置 | 初始建议 | 达到限制后的行为 |
| --- | --- | --- |
| 模型生成与修正 | 首次生成加最多 2 次修正 | 输出失败原因与恢复入口 |
| 活跃处理时间 | 每个任务暂定 120 秒，不包含等待用户操作 | 超时结束当前尝试，允许重新发起 |
| 浏览器反馈等待 | 暂定 10 分钟 | 标记等待过期，不继续修改页面 |
| 重复错误 | 相同错误连续出现 2 次 | 停止同类修正，提出不同实现或报告不支持 |
| 上传上下文 | 相关区域优先，限制元素数量、文本与截图尺寸 | 压缩或要求缩小改造范围 |
| 费用上限 | 根据供应商实测在设置中配置 | 达到上限停止继续调用 |

浏览器回执记录任务、尝试、方案版本和页面版本。重复回执幂等处理，过期回执不推进新任务。

## 新控件与原网站同步

布局修改继续使用原控件时，通常无需维护第二份业务状态。更换控件时，以原页面可观察的实际状态为准。

以颜色按钮改成下拉框为例：用户选择颜色，插件通过已验证的动作映射操作原控件，进入等待状态，原网站确认选中项后再读取价格、库存和图片，最后更新新界面。

第一版只实现一类可重复验证的简单映射。适配器提供读取状态、执行动作和确认结果的方法；程序触发动作不等于原网站接受了动作。若网站拒绝程序事件或状态不可确认，就恢复使用原控件。[事件可信标记说明](https://developer.mozilla.org/en-US/docs/Web/API/Event/isTrusted)

关键规则：

- 同一控件的动作串行执行，先避免并发请求混淆结果。
- 成功条件检查实际选中项及加载状态，价格不变也可能是正常结果。
- 原状态更新新控件时，不再次触发原动作，避免循环。
- 原目标被替换后先重新绑定，无法唯一匹配就暂停该控件。
- 商品切换后取消旧动作的等待；迟到结果不能作为新商品的结果。
- 验证阶段选择和比较规格，不执行真实下单或付款。

## 接口与事件设计

初始接口如下，具体字段由统一契约生成。服务端从认证上下文确定归属，不信任客户端传入的用户身份。

| 接口 | 行为 |
| --- | --- |
| POST /api/v1/tasks | 创建生成或继续修改任务，返回 taskId |
| GET /api/v1/tasks/{taskId} | 查询持久状态、当前尝试和最终结果 |
| GET /api/v1/tasks/{taskId}/events | SSE 推送事件，可按 afterSeq 续读 |
| POST /api/v1/tasks/{taskId}/feedback | 提交浏览器检查结果与受限截图 |
| POST /api/v1/tasks/{taskId}/cancel | 请求停止后续处理，已完成步骤不假定被撤销 |
| POST /api/v1/recipes | 保存服务端生成且浏览器检查过的方案 |
| GET /api/v1/recipes | 查询方案和版本历史 |
| GET /api/v1/recipes/{recipeId} | 读取某方案的版本与匹配范围 |
| POST /api/v1/recipes/{recipeId}/versions | 基于 baseRevision 保存新版本 |

启用、停用和切换方案的设备状态以本地存储为准。服务端保存方案内容和历史，不将云端有记录误认为当前浏览器已启用。第一版暂不实现跨设备启用状态合并。

SSE 事件包括 progress、explanation_delta、plan_candidate、awaiting_feedback、completed 和 failed。每个事件包含 taskId、seq、attempt 和时间。completed 事件及其最终结果必须在数据库持久提交后才发送；取消和等待过期也要有可查询的终态及对应事件。

断线后按任务 ID 和最后事件序号恢复。数据库状态是恢复依据，SSE 连接和浏览器内存不是。浏览器反馈使用普通 POST；认证需要自定义头时采用受控的流式 fetch 客户端，处理分段与重连，不假定原生 EventSource 支持任意请求头。

业务冲突约定：过期 revision 返回 409，用户保留当前修改并查看最新版本；格式错误返回 422；不存在或越权的资源按统一策略返回 404。错误响应包含可操作的原因，页面正文不能作为代码或提示指令执行。

## 数据库与任务恢复

| 表 | 主要内容 |
| --- | --- |
| tasks | 归属、请求摘要、状态、运行预算、当前尝试、租约、时间 |
| task_attempts | 快照引用、候选方案、模型信息、校验摘要、费用与耗时 |
| task_events | taskId 和 seq、事件类型、受限载荷，支持 SSE 恢复 |
| recipes | 归属、名称、匹配范围、当前版本引用 |
| recipe_versions | 不可变方案、定位描述、兼容性信息、来源任务 |
| task_feedback | taskId、attempt、planRevision、documentToken、检查结果 |
| workflow_checkpoints | LangGraph 当前执行状态，使用正式持久化组件 |

关系字段使用普通列，方案配置和报告采用 JSONB。依照真实查询建立索引，不提前索引整份截图或页面文本。

API 与 Worker 使用短事务。模型调用、等待浏览器和发送 SSE 不持有数据库事务或连接。任务事件与状态变化在同一事务提交，防止进度宣称完成而结果未保存。

单个独立 Worker 起步，使用数据库领取任务、租约和心跳。任务重复执行按至少一次交付设计：检查点、幂等键与 attempt 防止重复保存和重复应用。外部模型调用发生未知结果时，记录不确定性，不能承诺费用恰好发生一次。

Worker 中断后检查租约并恢复可重试阶段。处于等待浏览器状态的任务先等待有效反馈；页面已过期则结束本次任务或要求重新快照。

SSE 断开不默认取消任务。用户主动取消停止后续生成和修正，预览撤销由浏览器执行单独处理。

## 测试集与指标定义

第一轮核心集为 3 个淘宝实例乘以 4 个布局任务，共 12 个实际页面任务。受控页面的异常用例另行统计，不能把同一页面的多次重试当作独立成功任务。

后续拟扩充到至少 8 个页面实例，每个 6 个适用任务，共 48 个计划用例：3 个淘宝实例、3 个受控结构变体和第二类实际网站的 2 个实例。正式评测前确定具体内容和适用范围；不适用项单独报告，不悄悄缩小分母。

从中预留至少 2 个页面实例，不参与提示词和定位规则调试。报告分别展示开发集、留出集、真实网站与受控页面结果，注明同一网站模板会限制泛化结论。

| 指标 | 计算或判断方式 |
| --- | --- |
| 定位成功率 | 实际正确定位的目标数除以有明确标注的目标数 |
| 首次改造通过率 | 第一次生成同时通过布局和原交互检查的任务数除以任务总数 |
| 有限修正后通过率 | 在规定预算内完整通过的任务数除以任务总数 |
| 同类页面重用率 | 无新增逐页面规则即可应用的同类页面任务数除以相关任务总数 |
| 更新恢复 | 区分成功重绑、正确停止、未识别误改，不把正确停止计为恢复成功 |
| 原交互通过率 | 预先确定的交互检查项中实际通过的比例 |
| 撤销正确性 | 插件改造消失且网站最新数据和操作仍有效 |
| 延迟 | 分别记录采集、模型、校验、应用和总耗时 |
| 成本 | 每个任务的调用次数、token、供应商计费和修正成本 |
| 本地性能 | 观察通知数量、重绑次数、执行耗时、重复监听和页面卡顿情况 |

发布条件为核心场景全部通过、无已知静默误改或原交互破坏、所有明确不支持的能力可识别并停止。更大评测集的成功率按实际结果报告，不预先宣称达到某个百分比。

性能先取得基线，再在 M2 确定可重复的预算。建议初始关注相关区域扫描与样式应用的本地耗时，以及持续滚动和规格切换时是否产生明显卡顿；不同机器结果必须注明环境。

Playwright 扩展测试使用其支持的 Chromium 持久化上下文，不能直接沿用任意普通浏览器启动方式。真实页面依赖登录或出现验证流程时由用户手动完成，日常自动回归优先使用可控数据。[Playwright 扩展测试说明](https://playwright.dev/docs/chrome-extensions)

## 数据发送与运行边界

只有生成、继续修改和修复才发送相关页面上下文。已保存方案的重放和日常观察保留在本地，设置页面说明传给哪个模型服务、发送哪些字段。

默认排除密码字段、身份凭据、账户区和无关页面内容。截图仍可能包含非文本敏感信息，使用相关区域裁剪、明确区域遮罩和可查看的上传范围；不能仅靠删掉输入框文本就宣称完全脱敏。

模型密钥放在后端配置中，不能打包进扩展。个人部署默认只监听本机受控地址，并使用访问凭据；允许的扩展来源配置不替代认证。后续多用户版本增加服务端归属与访问控制的完整验收。

网页文本作为分析对象，不能改变模型的工具权限、接口地址或执行规则。普通布局配置不包含外部资源 URL、事件脚本和动态代码。日志默认记录区域数量、错误码和耗时，不保存整页正文、Cookie 或模型密钥。

截图和原始上下文在任务结束后按短期保留策略清理；方案和摘要保留用于恢复。具体保留时长作为部署设置，在 M4 明确并测试清理任务。

## 扩展分发与脚本增强路线

Manifest V3 要求扩展逻辑可从提交代码中辨认，普通远程数据不能包含执行逻辑。把复杂远程命令包装成 JSON 并构建解释器仍可能违反政策。内置配置执行器也必须按其实际能力检查，不能仅因采用 JSON 就认为符合分发要求。[Chrome Manifest V3 政策](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)

若后续需要超出内置能力的自定义逻辑，单独评估 User Scripts API。该 API 允许相应用途的用户脚本，需要权限和浏览器的允许用户脚本设置；政策例外只适用于对应 API 覆盖的代码，不保证整体产品通过审核。[User Scripts API 文档](https://developer.chrome.com/docs/extensions/reference/api/userScripts)

脚本增强模式是后续独立里程碑，需明确用户选择的脚本、作用网站、预览、停止和恢复能力。它不会消除 DOM 兼容性、事件限制和网页业务状态不可观察的问题。

## 主要风险与处理顺序

| 风险 | 首次验证阶段 | 应对与继续条件 |
| --- | --- | --- |
| 淘宝结构无法通过样式完成主要重排 | M1 | 验证受控结构改动与网站适配；原交互无法保留则调整实现或首个页面类型 |
| 节点移动破坏框架更新或事件委托 | M1 | 优先样式排列，要求节点更新和交互检查证据 |
| 元素定位不唯一 | M1 和 M3 | 局部上下文与实际匹配检查，必要时点选，无法确定则暂停 |
| 页面更新引起循环修改和卡顿 | M1 和 M2 | 观察范围限制、合并通知、变化归属标记和资源清理 |
| AI 生成可解析但不可执行的方案 | M3 | schema、目标和布局检查分别执行，记录不同失败原因 |
| 用户切页后迟到结果误应用 | M2 至 M4 | 文档与路由版本校验，执行前再次核对，过期任务回执拒绝 |
| 服务重启产生重复处理 | M4 | 租约、检查点、幂等保存，承认外部调用可能重复计费 |
| 新控件与原状态不一致 | M5 | 原状态确认、串行执行、超时失败和原控件恢复 |
| 改造方案触及扩展分发限制 | M0 和 M6 | 明确内置配置能力，检查相关政策，增强脚本单独评估 |
| 真实页面数据进入模型或日志 | M3 和 M6 | 局部收集、上传范围显示、受限日志与数据清理 |
| 泛化结论超过测试证据 | M5 和 M6 | 报告网站适配量、留出集和已知限制，按实测范围说明支持能力 |

## 首批可领取任务

下列任务可以直接进入开发看板，顺序体现依赖关系，预计工作量已包含在里程碑估算中。

- [ ] 建立独立 WXT 和 Vue3 扩展工程，能够打开侧边栏。
- [ ] 建立 PageContext 消息，完成侧边栏与当前文档通信。
- [ ] 制作可重复的动态商品测试页，支持规格、延迟和节点替换。
- [ ] 选择真实页面并保存基线，确定三栏改造的布局与交互检查。
- [ ] 点选与提取图片、介绍、购买三个区域，保存本次快照。
- [ ] 定义并验证第一版 ModificationPlan 契约。
- [ ] 使用手动方案应用三栏，完成溢出和关键控件检查。
- [ ] 实现撤销，验证网站最新选中状态仍然保留。
- [ ] 加入节点替换观察与重绑，证明不会重复注入。
- [ ] 在真实淘宝页验证规格切换并整理 M1 通过或失败报告。

第一项技术验收是手动方案驱动真实商品页三栏重排，并在更新和撤销后保留原交互。通过后再接入模型生成，减少把基础引擎问题误判成模型问题的机会。

## 每个阶段的完成记录

每次阶段结束写一份可复核记录：本次实现了哪些能力、使用哪些页面、通过与失败的任务、原交互和恢复结果、模型调用与成本、需要的网站适配、已知限制，以及下一阶段是否具备进入条件。

记录实际命令和环境版本，附必要截图、执行报告和代码版本。失败用例保留，修复后标注复测结果。文档中的计划标准与实际测量结果分开维护。

第一版演示应展示一条真实流程：输入要求、布局预览、连续修改、原控件操作、保存、刷新、同类页面、动态更新、撤销。对不兼容页面展示明确停止和恢复方式。

后续优先级依据个人使用记录和评测结果决定：更多网页结构、更强控件映射、可分享方案、多设备同步，最后再考虑商业化外围功能。
